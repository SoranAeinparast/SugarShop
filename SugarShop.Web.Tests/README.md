# آزمون‌های خودکار SugarShop (پروژه‌ی SugarShop.Web.Tests)

هدف اصلی این پروژه، **قفل‌کردن جداسازی «اپلیکیشن» و «وب‌سایت»** است تا همان باگی که تجربه‌ی کاربر را
خراب می‌کرد (باز شدن چیدمان اپ در مرورگر یا ظاهر شدن صفحه‌ی وب داخل اپ) دیگر برنگردد.

## اجرا

```bash
dotnet test SugarShop.Web/SugarShop.Web.sln
```

همین دستور در CI هم اجرا می‌شود: `.github/workflows/tests.yml` روی هر push و pull request.

یا فقط همین پروژه:

```bash
cd SugarShop.Web.Tests && dotnet test
```

هیچ پیش‌نیازی ندارد: نه SQL Server، نه سرور در حال اجرا، نه ورود دستی. آزمون‌ها کل برنامه را در حافظه
اجرا می‌کنند (کلیدواژه `Testing`)، هر سه `DbContext` را با نسخه‌ی in-memory جایگزین می‌کنند و کاربر را با
یک اسکیم احراز هویت آزمون وارد می‌کنند.

> ⚠️ اگر سرور توسعه (`dotnet run` در `SugarShop.Web`) در حال اجرا باشد، خروجی بیلد را قفل می‌کند و
> `dotnet test` با خطای `MSB3027/MSB3021` (فایل `SugarShop.Web.dll` در حال استفاده است) شکست می‌خورد.
> پیش از اجرای آزمون‌ها سرور توسعه را ببندید.

## قاعده‌ای که آزمون‌ها از آن محافظت می‌کنند

1. حالت صفحه **فقط** از User-Agent پوسته‌ی اندرویدی (`SugarShopApp/`) تعیین می‌شود — تنها منبع حقیقت
   `Helpers/AppClient.IsAppRequest` است.
2. همان تصمیم اول روی `<html data-app-mode="inapp|browser">` نوشته می‌شود (بدون پرش و بدون اجرای JS).
3. هیچ عنصری بیرون از حالت خودش رندر نمی‌شود:
   - `data-ui-scope="app"` → فقط درخواست اپ
   - `data-ui-scope="web"` → فقط درخواست مرورگر
4. هیچ کوکی/حافظه‌ای حالت صفحه را نگه نمی‌دارد (کوکی قدیمی `appmode` کاملاً بی‌اثر است).

| `AppModeSeparationTests.cs` | ماتریس کامل صفحه‌ها (`TestPageCatalog`) در هر دو حالت: نبود عنصر اپ‌محور در وب و برعکس، بنر نصب، آیتم‌های نوار پایین، کلاس `header-fixed` و صفحه‌ی سند صورت‌حساب |
| `AppModeInvariantsTests.cs` | کوکی کهنه حالت را عوض نمی‌کند، هیچ پاسخی کوکی حالت نمی‌نویسد، حالت مخصوص هر درخواست است |

| `ModeSourceContractTests.cs` | نگهبان روی فایل‌های منبع: نویسنده‌ی `data-app-mode` باید `AppClient` باشد، نام کوکی قدیمی جایی جز لیست مجاز نباشد و حصار محیط `Testing` سر جایش بماند |
| `OrderPricingServiceTests.cs` | 💰 ریاضیات پول: محصول + جعبه‌ی وزن‌کشی‌شده + پیک − تخفیف، ارسال رایگان، جعبه‌ی وزن‌کشی‌نشده، پرداخت‌های قبلی و برابری محاسبه‌ی گروهی با تک‌سفارشی |
| `OrderInternalMarkerTests.cs` | 🧭 ستون نشانگر «سفارش داخلی»: هم‌ارزی مقدارش با قاعده‌ی پیشین Notes، نبود فیلتر متنی روی Notes در هیچ کوئری، و درستی مهاجرت (پرکردن سفارش‌های موجود + ایندکس پوشا) |
| `AdminOrdersListTests.cs` | 📄 لیست سفارش‌های پنل مدیریت: صفحه‌بندی و جست‌وجو سمت سرور (ردیف‌های HTML فقط همان صفحه‌اند)، شمارنده‌ی تب‌ها و جمع مبلغ روی کل مجموعه‌ی فیلترشده، فیلتر همه‌ی وضعیت‌ها، حذف سفارش‌های داخلی و هم‌فیلتر بودن خروجی اکسل |
| `PaymentReminderTests.cs` | 📨 یادآوری خودکار پرداخت: فقط سفارش واجد شرط، یک‌بار، با مبلغ/لینک درست، و بی‌اثر شدن درست وقتی تنظیمات یا قالب مشکل دارد (هیچ پیامک واقعی ارسال نمی‌شود) |
| `Infrastructure/` | میزبان آزمون، احراز هویت آزمون، فهرست صفحه‌ها و ابزار خواندن HTML |

## افزودن صفحه‌ی تازه

اگر صفحه‌ای با رندر شرطی اپ/وب اضافه شد، آن را در `Infrastructure/TestPageCatalog.cs` ثبت کنید؛
ماتریس آزمون خودش آن صفحه را در هر دو حالت بررسی می‌کند. برای بخش‌های مخصوص هر حالت، صفت
`data-ui-scope="app"` یا `data-ui-scope="web"` را روی همان عنصر بگذارید (و رندرش را سمت سرور شرطی کنید).
